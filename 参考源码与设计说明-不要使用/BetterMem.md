# PhaseKV 的显存、访存与首次冷却优化

在 RTX 4090 的 Llama-3.1-8B-Instruct 定版测试中，8192 输入、2048 输出、batch 6 的最终 KV 从 Full FA2 的 **7.50 GiB** 降到 PhaseKV 的 **2.43 GiB**，整批解码吞吐从 **132.01** 升到 **164.99 token/s**。但 PhaseKV 在预填充和打包时仍达到 **22.99 GiB**。同一张卡上，9192 输入的 batch 6 就卡在这个阶段。理解这两个结果，要分别看**哪些数据常驻显存、每次注意力怎样读取这些数据，以及创建和更新缓存时哪些分配会同时存在**。[定版批量实测](PhaseKV与Full消融/4090_batch2_6_fAryLQ4D/summary.json)

下面按实现演进说明。**旧版**有两个具体参照：2026-10-25 的单层测试对比“逐段启动”和“统一分段内核”；2026-10-27 的 P1–P5 优化从**已经有两次注意力启动**的版本出发。11 月的冷却 A/B 又从已有通道连续 K、环形热区和 GQA 复用的版本出发。每一处收益都用它自己的对照组，不能把几张卡、几个模型的百分比连乘成一个总加速比。[分段内核验证](results/phasekv_segmented_decode_validation_20261025.json) · [P1–P5 交付记录](docs/experiments/optimization_delivery.txt) · [4090 定版提交](https://github.com/kladjf666-commits/PhaseKV/commit/e9e898e)

## 1. 先减少常驻 KV，再减少搬运

早期仓库保留了伪量化路径，用来观察数值误差。把数值舍入后继续放在浮点张量里，底层存储仍占浮点字节。正式 PhaseKV 把码值写进 `uint8` 张量，一个字节放两个 4-bit 码，另存 FP16 的 `scale` 和 `min`。每层缓存按生命周期分开管理：

| 区域 | 何时写 | 解码怎样读 | 空间与代价 |
|---|---|---|---|
| Prompt | 先读完整输入；需要淘汰时，用末尾观察窗口的注意力按 KV 头选位置，按原顺序收集，再一次打包 | 后续直接读冻结的码与元数据 | 保留率决定存多少位置；量化决定每个位置占多少字节。100% 保留也可以用 4-bit |
| Hot | 当前生成 token 的已加 RoPE 的 K 与对应 V 按层追加 | 直接读 FP16 | 最近 128 个受保护，另预留 16 个待冷却位置；容量 144，正常步末实际有效长度会变化 |
| Cold | 凑齐 16 个可冷却位置后，按各层、各 KV 头的 V 范数选择，按时间顺序打包 | 直接读冻结段，后续追加新段 | 冷区配置 0.80 时每组留 13 个，实际为 81.25%；已冻结的历史不用反复解压、合并、重新量化 |

以 32 层、8 个 KV 头、头维度 128 的 Llama 为例，单序列每增加一个完整的 FP16 KV 位置，消耗 `32 × 8 × 128 × 2(K,V) × 2 字节 = 128 KiB`。4-bit 码本身只要原来的四分之一；按 32 个标量一组，还要存 4 字节的 scale/min，所以满组平均是 `0.5 + 4/32 = 0.625` 字节/标量。短冷段、末尾补齐、FP16 热区和空闲页槽都会改变实测比值。淘汰只改变物理驻留位置数；后续 RoPE 位置按实际经过的 token 数推进。[缓存生命周期](PhaseKV/phasekv_cache.py) · [prompt 选择](PhaseKV/prompt_tier.py) · [打包格式](PhaseKV/kernels/packing.py)

单序列 Llama 的预填充也有一次内存取舍。选择器只需要最后 32 个 query 对历史位置的注意力。实现用 FA2 先跑前缀，只在末尾观察窗口取显式注意力，再据此选择并打包。对 8192 个输入位置，每个头需要保留的打分矩阵从完整的 `8192 × 8192` 缩成 `32 × 8192`。这减少了为选择而保存的注意力分数；预填充阶段仍会建立 dense KV。后文的多序列测试固定 prompt 保留 100%，直接分块预填充后打包，省去了选择分数的需要。[单序列预填充](official_llama/native_runtime.py) · [多序列预填充](workspace_migration/quick_4090d/batch_speed.py)

## 2. 从逐段启动到两次注意力启动

旧逐段参考实现遍历 prompt、后续追加的 prompt 段和各个冷段，分别发起计算；热区另算，最后合并。即使每段都已经是压缩格式，生成越长，Python 遍历、内核提交和中间结果越多。另一条用来做消融的路径把压缩 KV 临时还原成完整 FP16，再交给 FlashAttention 2。它保留了低位常驻缓存，但每步多出解包写显存、再读 FP16 的往返。[旧逐段参考实现](PhaseKV/kernels/attention_triton.py) · [显式解包消融](official_llama/ablation_kernels.py)

统一内核给每个冻结段登记描述行。行里有 K/V 码、scale、min 的六个指针，处理的 token 范围，以及位宽、组长、步幅。数据可以留在不同的页里。每层每个解码步的注意力有两次 GPU 启动：

1. **分段主核**按头和 token 范围分工。块内从显存读取低位码和元数据，在计算中还原 `code × scale + min`，算 `Q·K / √D` 并加权 V。每个局部结果只写 FP32 的最大分数 `m`、相对该最大值的指数和 `l` 与加权向量 `a`。热区使用同一归约方式直接读 FP16。
2. **归并核**令 `M = max(m_i)`，输出 `Σ exp(m_i−M)·a_i / Σ exp(m_i−M)·l_i`。因此不同段共享整段历史的 softmax 分母，不必写出完整 logits 或完整反量化 KV。归并本身也分块，限制寄存器占用。

RTX 4090D 的早期实测如下。形状为单层、28 个 query 头、4 个 KV 头、头维度 128。单位是**同步墙钟毫秒/层/步**，包含 Python 提交，不含整模型和冷却。最后一列反映同一个新内核如果当次还要重建描述表，调用成本会怎样变化。

| 冷段数 | 旧逐段路径 | 新两启动，复用描述表 | 新两启动，含重建 |
|---:|---:|---:|---:|
| 0 | 0.427 | 0.077 | 0.171 |
| 16 | 3.086 | 0.077 | 0.343 |
| 125 | 20.991 | 0.095 | 1.497 |
| 253 | 41.272 | 0.168 | 2.754 |

253 个冷段时，去掉逐段提交带来了很大的单层收益；同一行的 **0.168 → 2.754 ms** 又解释了为什么值得做下一轮描述表复用。固定两次启动只约束主核和归并的调用数；随着上下文增长，要读的 KV、要算的分数和部分结果仍会增加。[单层原始计时](results/phasekv_segments_4090d.json) · [主核与归并](PhaseKV/kernels/segmented_attention.py)

## 3. P1–P5 分别改了哪一次读、写或分配

| 阶段 | 优化前付出的成本 | 改法与实际边界 |
|---|---|---|
| P1 融合量化 | 求极值、缩放、舍入、打包经多个张量操作，中间码值需要存储 | Triton 从原始 stride 读输入，在一个量化核中按组求 min/max、算 4-bit 码并直接写目标槽和元数据；K、V 各按自己的轴调用。末尾不足一字节会屏蔽无效码。不支持的形状沿用参考打包路径 |
| P2a 描述表与工作区复用 | 新增冷段时，重建已有描述行、重新分配各头的 FP32 临时缓冲 | 每层保留段所有者、有效行数和预留容量。容量够时只追加新行；满了按几何级数扩容。内核只遍历有效行。设备、流、调度、prompt 段或冷段分组方式变化时才按需重建 |
| P2b 冷段分页 | 每个小冷段单独申请 K/V 的码、scale 和 min，共六份小存储 | 同一布局使用追加式页池，每页 32 个槽；每段持有槽的视图，量化直接写入槽。减少分配次数，但新开页会有空槽，分段量化边界不变 |
| P3 冷段分组 | 很短的冷段各自产生局部结果，归并核需多读写许多份 `m/l/a` | 长 prompt 仍可切为多个 split；足够多冷段时，一个工作单元最多连续处理 8 个短段，只写一份局部结果。每段仍使用自己的 scale/min；不足 8 段时使用单段调度 |
| P4 四位专用读取 | 通用路径逐段加载位宽、组长并求索引 | 已验证的 4-bit 布局使用固定移位、掩码和组索引。32-token prompt K 组与 32-channel V 组有专用寻址；16-token 冷块以及后续 13-token 布局有各自的兼容检查，不匹配则走通用读取 |
| P4 的独立 GQA 开关 | 多个 query 头共用同一 KV 头，但分别处理时会重复读码、反量化 | 将同一 KV 头对应的 query 头放在同一 Triton 程序内，共享 K/V tile，各自计算分数和累加。Llama 32Q/8KV 对应 4 个 query 头一组。实际吞吐还取决于并行度与寄存器占用 |
| P5 环形热区 | 移走最旧 16 个位置后，把仍然有效的热 KV 整体搬回数组开头 | 预留固定容量，以 `hot_start`、`hot_len` 表示逻辑顺序。追加和读取用 `(hot_start + 偏移) % 容量`；冷却只推进起点。需做 TopK 时最多整理待筛的旧块，保留的 128 个位置留在原处 |

长段的 split 数、每块 token 数和 warp 数根据实际保留长度、头数、头维度与 GPU 的 SM 数选择；小块限制同时驻留的反量化元素，避免为短段发空 split。P5 的历史阶段从 P4 加环形缓冲，**没有自动启用 GQA**；11 月 Llama 定版另行显式启用 GQA 和通道连续布局。[阶段开关](PhaseKV/optimizations.py) · [融合量化核](PhaseKV/kernels/quantize_triton.py) · [页池](PhaseKV/packed_storage.py) · [工作区](PhaseKV/kernels/segmented_plan.py) · [调度](PhaseKV/kernels/launch_config.py)

**P5 整体对照。** 2026-10-27，RTX 4090D、Qwen2.5-7B-Instruct、1024 输入 + 4096 输出，prompt 保留 70%、冷区留 16/16。保存的两启动基线 → P5，解码时间 **122.26 → 110.51 秒**，吞吐 **33.49 → 37.05 token/s（+10.63%）**，实际 KV **94.46 → 97.17 MiB**。这是预热后每版一次的长输出初筛，只能归因到这一组改动。分页为什么可能多占空间，可以在独立 CPU 容量审计中直接看到：单层、717 个 prompt 位置、7 个冷段、143 个有效热位置，底层 KV 从 **834,112 增至 1,115,712 字节**，差额 **281,600 字节**正好是空闲页槽。[长输出原始结果](results/downloads/20261027_long_output_p5/results/phasekv_long_output_quick_001/summary.json) · [逐阶段容量审计](results/phasekv_optimization_20261027/cpu_audit.json)

## 4. 为什么新布局的 K 地址加 1 就能读下一通道

这里的“通道”是**同一个 KV 头内的特征维度** `d`。K 沿 token 轴量化：固定 batch、头和通道，同一组时间位置共享 scale/min；两个相邻时间位置的 4-bit K 码组成一个字节。令 `t` 为段内位置，`j = t // 2` 为码字节序号，`J = ceil(T/2)`，`D` 为头维度。以下固定 batch 和头，以该头起始地址为基址：

| K 码布局 | 物理连续顺序（由慢到快） | 访问 `(t,d)` 的字节偏移 | 同一 t，从 d 到 d+1 |
|---|---|---|---:|
| 旧 | 通道 d、字节 j | `d × J + j` | +J 字节 |
| 通道连续 | 字节 j、通道 d | `j × D + d` | **+1 字节** |

举例：`T=64, D=128, t=5`，码字节下标为 `j=2`，取其高 4 位。读通道 9、10 时，旧地址偏移分别是 **290、322**，新地址分别是 **265、266**。新布局中，这两个相邻字节分别装着通道 9、10 的 token 4/5 码。取 `t=4` 用低半字节，取 `t=5` 用高半字节。访问 `t+2`、保持通道不变，则要跨 **128 字节**。这次调整让处理同一时间位置的一排通道可以连续读取；它改变的是物理步幅，K 的量化轴仍是时间。

写入侧的 `empty_packed_storage` 先按物理形状 `[B,H,J,D]` 分配，再用 `transpose(-2,-1)` 提供逻辑视图 `[B,H,D,J]`。此时最后两维的 stride 为 `(1,D)`，转置只改视图；量化核接收这些 stride，直接写最终地址，读取前不需要再拷贝整段。scale/min 同理，逻辑索引 `[d,g]` 的物理偏移为 `g × D + d`。它们的元素是 FP16，**加 1 个元素等于加 2 字节**。V 则按每个 token 的通道分组，一个码字节装两个相邻通道，读取时用 `d//2` 和 `d%2` 取码。[分配与逻辑视图](PhaseKV/kernels/packing.py) · [写入目的 stride](PhaseKV/kernels/quantize_triton.py) · [读取实际地址](PhaseKV/kernels/segmented_attention.py)

进入专用路径前，描述表逐段验证 K 码和元数据的通道 stride 为 1，且非单例的字节/组维 stride 为 D。prompt 的组号可用 `t >> 5`。冷区留 13/16 时，一个段只有 13 个有效位置，K 的实际组长为 13，只有一份 scale/min；在有效范围 0–12 内，`t >> 4` 始终是 0。内核屏蔽尾部后仍可走同一冷块快路径。V 继续按 32 通道一组。[专用布局检查](PhaseKV/kernels/segmented_plan.py)

**实测能省多少读取时间？** 11 月 1 日，RTX 3070 Ti Laptop，固定 Q/KV，Llama 头形状 32Q/8KV，8K 输入、1 个冷段，仅切换 K 的布局及相应读取路径。分段主核 **558.46 → 462.26 µs**；32 个冷段时 **607.98 → 502.12 µs**。这是预热后 CUDA Graph 重放的主核时间，不含归并和模型前向。8 组头数与长度组合的归并后输出最大绝对差均为 0。另一项同机实验固定新布局，再开启 GQA，8K、1 个 13-token 冷段的主核 **470.99 → 286.63 µs**。换到 4090D、完整 32 层模型、8192+256，GQA 关闭/开启的吞吐中位数是 **37.22 / 37.56 token/s**，三轮配对增益中位数 **+0.99%**。[布局微基准](PhaseKV与Full消融/分段主核本地验证.json) · [GQA 微基准](results/local_gqa_reuse_20261101/llama_4layer_and_kernels.json) · [4090D 整模型 GQA 对照](PhaseKV与Full消融/4090d_speed_20261101_221816_361/summary.json)

## 5. 首次冷却有两个尖峰，分别发生在第 144、145 步

第 1 个输出 token 来自预填充；下文“解码第 1 步”指把这个 token 送回模型。每层先把当前 K/V 写入热区，再做注意力；所有层读完后，`finish_decode_step()` 才统一冷却。以热窗口 128、懒批 16 为例：

```text
第 143 步结束     hot 有 143 个，cold 为空
第 144 步注意力   先读 144 个 hot，仍未读到生成冷段
第 144 步末       最旧 16 个选出 13 个并打包 → cold 有 1 段，hot 留 128 个
第 145 步注意力   追加本步后有 129 个 hot；首次登记并读取新 cold 段
第 146–159 步     复用这张描述表；hot 长度与第 130–143 步逐一对应
```

**先定位。** 在 4090D 上追踪同一条生成，CUPTI 记录到第 144 步末缓存维护的 GPU 时间相对冷却前增加 **0.899 ms**；第 145 步首次读冷块相对同热长度的第 129 步，描述表/工作区 GPU 时间增加 **0.040 ms**。为测正常运行的 CPU 成本，另一次关闭 CUPTI，只计调用线程的时钟，并与未插桩运行配对。第 144 步的 `cache_finish` 多用 **11.412 ms 线程 CPU**；第 145 步的工作区维护多用 **2.289 ms 线程 CPU**。冷块已建好后，第 146–159 步相对第 130–143 步，三项缓存维护合计仅多 **0.004 ms 线程 CPU/步**。轻量计时对整个 31 步窗口的配对墙钟扰动中位数为 **+0.85%**。GPU 活动、线程 CPU 和整步墙钟各有自己的起止点，期间可以重叠。[GPU 分段跟踪](PhaseKV与Full消融/4090d_first_cooling_kO5Rd3XM/cooling_summary.json) · [关闭 CUPTI 的 CPU 对照](PhaseKV与Full消融/4090d_cooling_cpu_IaF5gQxk/cpu_summary.json)

**第 144 步改了写入。** 旧路径的 32 层各自调用范数、TopK、排序、Gather 和 K/V 打包。优化后的 `_cool_batch` 取每层最旧的 16 个 K/V，沿新维度叠成 `[层, KV头, 16, D]`。范数只沿 D 求，TopK 和排序只沿这 16 个位置做，因此每层、每个头仍独立选取 13 个。一次批量收集后分别发起 K 和 V 打包，共用一个跨层页槽；按层切成视图交还给各层，不复制码和元数据。之后各层只追加段引用并推进热区起点。减少的是重复的主机派发和小分配，仍有组合这批输入的 `cat`、收集以及首次开页成本。不满足既定形状、位宽或保留策略时沿用逐层路径，包括保留 16/16 的对照组。[跨层冷却与回退](PhaseKV/phasekv_cache.py)

**第 145 步改了登记。** 原来每层先在 GPU 上构造一个临时描述行张量，再复制到正式描述表。现在 `_write_rows` 在 CPU 组织新的整数行，以 `descriptors.narrow(...).copy_(source, non_blocking=True)` 直接写到 GPU 表的最终位置。已有行继续使用；仍需传输新增行，每层首次读新段仍会触发检查。描述表或局部结果空间不足时也仍需扩容。[描述表写入与扩容](PhaseKV/kernels/segmented_plan.py)

**再做同卡旧/新对照。** RTX 4090、同一 32 层 Llama、8192+256、batch 1、prompt 70%、冷区 80%、GQA 开启。两组各预热，取两轮正式配对。下表前两行是目标函数相对参照步**多出来的主机经过时间**；整步墙钟来自轻量插桩窗口，全程吞吐来自独立的无插桩运行。

| 测量项 | 旧 80% | 新 80% | 读法 |
|---|---:|---:|---|
| 第 144 步 `cache_finish` 增量，相对 130–143 步均值 | 9.091 ms | 1.475 ms | 少 **7.615 ms**，约降 84% |
| 第 145 步工作区维护增量，相对第 129 步 | 3.716 ms | 1.898 ms | 少 **1.818 ms**，约降 49% |
| 第 144 步整步墙钟 | 29.520 ms | 22.034 ms | 新版冷却前普通步约 21.256 ms，仍能看到首个冷块的成本 |
| 第 145 步整步墙钟 | 26.047 ms | 25.447 ms | 组件省下的时间只部分体现在整步上 |
| 全程 255 步，ms/token | 21.451 | 21.322 | 每步平均少 0.128 ms |
| 全程吞吐，token/s | 46.62 | 46.90 | 配对提升 **0.60%** |
| 最终 KV，字节 | 273,899,520 | 273,899,520 | 输出 token 哈希也一致 |

同次实验还在**更新后的代码**上比较了两种保留策略。冷区留 13/16 与留 16/16 的最终 KV 分别为 **273,899,520 / 276,914,176 字节**，吞吐分别为 **46.90 / 46.91 token/s**。前者走跨层选择打包，后者免选、逐层打包。这个短输出提示只生成 7 个冷段，裁掉部分冷 KV 节省了约 **2.88 MiB**，两种策略的全程速度几乎相同。

这是**每条生成首次建冷块**的改进。另一个问题是进程第一次触达某个 Triton 形状时的编译和运行时初始化。4090D 原始记录中，未插桩预热轮第 144 步为 **89.65 ms**，正式轮中位数为 **37.19 ms**；记录没有把其中的编译、分配等因素单独计时。测速入口用完整生成做预热，使首次打包和首次读冷块都被执行；仅预热 prefill 或不足 144 步无法覆盖这两条路径。上表的 84% 与 49% 是预热后仍然存在的逐请求开销改善，不代表新进程的首次调用已无延迟。[4090 同卡逐轮 A/B](PhaseKV与Full消融/4090_cooling_retention_6Ed7ciwp/summary.json) · [差值的计算方法](workspace_migration/quick_4090d/compare_cooling.py) · [测速预热入口](workspace_migration/quick_4090d/full_speed.py)

## 6. 整模型为什么只得到一部分主核收益

早期 RTX 4090 四路径消融使用同一个 8192+256 提示。Full+FA2、PhaseKV 显式解包+FA2、PhaseKV 直接读压缩 KV+Triton 的整步时间分别为 **26.58、35.01、29.37 ms/token**。显式解包在独立采样的 16 步内平均占 **3.34 ms GPU 时间/步**。直接读取省去了这次完整的 FP16 落地，但还有解码投影、MLP、缓存维护、反量化和归并。在融合路径的 GPU 轨迹中，模型矩阵向量乘约 **16.38 ms/步**，分段注意力含归并约 **4.42 ms/步**。单层布局改善只影响后者的一部分。正式整步墙钟和独立采样的 GPU 事件不用于相减推算 CPU 时间。[原始消融与计时口径](PhaseKV与Full消融/READ.md)

定版 RTX 4090 改用 prompt 保留 100%、冷区 13/16，与同卡 Full FA2 比较。单序列、8192+2048，吞吐 **44.56 → 44.72 token/s**（三轮配对 +0.37%）；9192+256 则为 **44.50 → 44.19**（−0.70%）。批量适配在同一步推进各条序列，把 PhaseKV 的批次和 KV 头映射到独立的头索引，一次分段计算覆盖整批；每条序列仍有自己的 KV，同组 query 共用的 KV 头也不变。批量测试双方都按 512 个输入位置分块预填充。[定版单序列结果](PhaseKV与Full消融/4090_prompt100_speed_2cases_VjjdG5Fk/summary.json) · [批量适配](official_llama/ablation_attention.py)

| 8192+2048，batch 6 | Full FA2 | 定版 PhaseKV | 测量范围 |
|---|---:|---:|---|
| 最终 KV | 7.50 GiB | 2.43 GiB | KV 底层唯一存储；包含分配给页和热区的容量 |
| 解码峰值 | 22.59 GiB | 17.65 GiB | PyTorch 活跃分配，包含权重、KV 和临时张量 |
| 预填充及打包峰值 | 21.31 GiB | 22.99 GiB | PhaseKV 此时持有 dense KV，同时逐层建立 packed KV |
| 整批吞吐 | 132.01 token/s | 164.99 token/s | 排除首 token，完整预热一次、正式一次 |

显存账应分别看有效码、scale/min、有效热 KV、空闲容量、辅助工作区和进程峰值。多个层视图引用同一页时，按底层存储去重；`physical_bytes` 统计 KV，描述表和归并工作区另列。由于解码峰值少了约 **4.94 GiB**，仅看解码容易高估可用 batch。9192+256、batch 6 的失败发生在 `pack_prompt`：当时 GPU 仅余 **1.75 MiB**，下一次申请 **28 MiB** 失败。512-token 的分块限制了单次前向的长度，但当前批量实现仍先累积完整 dense prompt，再转换成 packed cache。逐层打包后及时释放 dense 所有权是针对这个峰值的后续方向，定版结果记录的是现有实现。[显存记账](PhaseKV/phasekv_cache.py) · [批量预填充和打包](workspace_migration/quick_4090d/batch_speed.py) · [分阶段峰值与 OOM 原始记录](PhaseKV与Full消融/4090_batch2_6_fAryLQ4D/summary.json)

最后还有一个直接影响字节数的参数：prompt 保留率。它与 4-bit 内核、冷却实现属于不同的实验变量。七档质量扫描对同一批 1600 道子题按题号核对后，95% 与 100% 的三任务平均准确率分别为 **62.19% 和 61.20%**；上面的定版吞吐和显存表均用 **100%**。在选择更低保留率时，应对照相应质量结果，不能直接沿用另一档的吞吐或正确率。[质量扫描](PhaseKV与Full消融/4090_prompt_quality_scan/summary.json)
