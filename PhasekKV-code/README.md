# PhasekKV-code 的预填充显存优化

保留参数与解码内核不变，通过逐层释放观察窗口注意力、消费式打包旧KV和消除多余视图引用降低峰值。

## 1. 最终缓存很小，为什么运行峰值仍然很高

最终 KV 是预填充、选择、打包和生成完成后留下的缓存。峰值显存则取决于整个过程中某一时刻同时存活的数据：

```text
峰值显存 = max_t {
    模型权重
  + 时刻 t 仍存活的完整 FP16 KV
  + 时刻 t 已创建的量化 KV
  + 时刻 t 仍存活的注意力权重
  + 选择、收集、量化及其他计算的临时空间
}
```

这里是先计算每个时刻的合计再取最大值，不能把各类张量分别出现过的最大值直接相加。

旧实现先生成完整 FP16 KV，再收集所有层的观察窗口注意力，最后统一选择和打包。新缓存逐层建立时，完整旧缓存和各层注意力仍被引用。最终只需要一份压缩缓存，转换过程中却可能同时保留多份大张量。

因此，降低最终 KV 的位宽或位置数，不会自动消除转换阶段的峰值。

## 2. 旧流程中的两种大规模重叠

### 2.1 所有层的观察窗口注意力一直保留到打包阶段

PhaseKV 使用末尾 32 个查询位置的注意力，对 Prompt 位置进行投票和选择。旧速度入口调用模型时设置 `output_attentions=True`，模型返回所有层的注意力，再统一调用 `select_prompt_indices()`。

```text
完整 FP16 前缀缓存
  → 计算观察尾部，并积累第 1～32 层注意力
  → 根据这些注意力选择各层位置
  → 保留所有注意力，同时逐层量化打包 KV
  → 返回后才释放不再需要的旧对象
```

不需要保存完整的 N×N 注意力矩阵，但“观察窗口 × 上下文长度”再乘上 Batch、查询头和层数，仍然很大。

以 N=32768、B=8、32 层、32 个查询头、8 个 KV 头、头维 128 为例：

| 张量 | 形状与字节计算 | 体积估算 |
|---|---|---:|
| 全层 FP16 Prompt KV | 32层 × 8请求 × 8个KV头 × 32768位置 × 128维 × K/V两份 × 2字节 | 32 GiB |
| 全层观察窗口注意力 | 32层 × 8请求 × 32个查询头 × 32个观察位置 × 32768键位置 × 2字节 | 16 GiB |
| 单层观察窗口注意力 | 上一行除以32层 | 0.5 GiB |
| 全层选中位置下标 | 32层 × 8请求 × 8个KV头 × 29491位置 × 8字节 | 约0.45 GiB |

29491 是 `round(32768 × 0.9)`。注意力按32个查询头计算，下标经原有GQA聚合后按8个KV头保存，二者不能混用。

这些是张量尺寸估算，不是逐分配显存剖析。注意力计算、FP32投票、池化和排序还有临时空间。例如将单层 FP16 注意力转为 FP32 会产生额外张量，所以“只保留一层注意力”不等于该阶段总共只占0.5 GiB。

### 2.2 打包完成的层，其完整旧 KV 仍留在源缓存里

旧 `from_dense_prefill()` 默认不修改输入缓存。它逐层读取完整 K/V、收集选中位置、量化并建立新的 Prompt 层，但输入对象的 `key_cache` 和 `value_cache` 继续持有全部原始张量。

随着新量化缓存增长，旧的完整缓存并没有同步缩小。对于上述场景，32 GiB 的原始 Prompt KV 会与逐步形成的量化 KV 重叠。

另一个容易忽略的问题是视图引用：如果为了批量解码另外建立一套 reshape 后的张量列表，即使清空其中一个列表，另一个列表仍可能持有相同底层存储。只删除一个变量名，并不保证底层显存可以复用。

旧速度路径见 [benchmark/baseline_runtime.py](benchmark/baseline_runtime.py) 中的 `speed_prefill()` 和 `flatten_requests()`。

## 3. 逐层处理怎样缩短张量的生命周期

### 3.1 当前层算完，立即选取位置，然后释放注意力

[memory_prefill.py](PhaseKV/memory_prefill.py) 中的 `capture_indices()` 临时包装每层原始注意力前向：

1. 仍然执行原来的 eager 观察窗口注意力计算。
2. 立刻将该层权重交给原来的 `select_prompt_indices()`，得到相同规则下的选中位置。
3. 释放该层注意力权重，向外返回 `None` 作为注意力权重项。
4. 跨层只保存选中位置下标，继续下一层计算。

外层模型调用使用 `output_attentions=False`，但包装器在本层内部仍显式请求权重。这样模型不会再构建保存全层大张量的 `all_self_attns` 集合。

```text
第1层：计算注意力 → 选择位置 → 释放权重 → 保存下标
第2层：计算注意力 → 选择位置 → 释放权重 → 保存下标
……
第32层：计算注意力 → 选择位置 → 释放权重 → 保存下标
```

这项改变把跨层累计的注意力权重改为当前层使用完即可回收。权重相关的存活规模由约 `层数 × B × 查询头 × 观察窗口 × N` 降为当前层所需规模，同时仍需保存全层位置下标。

选择函数、观察窗口32、maxpool核7、GQA聚合、保留预算和时间顺序都沿用原实现。只要本层权重相同，提前执行本层选择不需要等待后续层，也不会改变本层已计算的隐藏状态。包装在正常退出和异常退出时都会恢复原始前向方法。

### 3.2 每层打包后，立即释放该层完整 KV

[phasekv_cache.py](PhaseKV/phasekv_cache.py) 的 `PhaseKVCache.from_dense_prefill()` 增加了显式参数：

```python
consume_dense_cache=True
```

优化入口将源缓存的所有权交给打包函数。每层量化成功后执行：

```python
keys[layer_idx] = None
values[layer_idx] = None
del key, value
```

于是打包过程变成：

```text
完整旧KV逐层减少  ←  当前层收集与量化  →  新量化KV逐层增加
```

后续层不会用到已经完成打包的旧层 K/V，因此可以释放其引用。每个量化层仍包含相同的数据码、scale/min和原有缓存结构。

此参数默认是 `False`，保留原有调用者不修改输入缓存的约定。开启后，源缓存已被消费，不能再次用于前向或重试；若中途出错，也可能处于部分消费状态。调用者必须保证不再需要它，并且不保留原始张量的额外引用。

### 3.3 批量展开直接更新源列表，避免额外视图保活

批量解码沿用原有映射：

```text
[B, Hkv, N, D] → [1, B×Hkv, N, D]
```

`flatten_owned_cache()` 在原来的 K/V 列表中替换张量，并以相同顺序展开下标。它不再额外创建一个持续持有所有层视图的缓存对象。

这一点与消费式打包配合，确保清空某层列表项后，不会因适配代码保留另一份视图列表而使大块存储继续存活。reshape 是否复制取决于张量布局；无论是否为视图，都需要明确管理持有它的引用。

释放引用使存储在满足CUDA执行依赖后可被分配器复用，并不保证立即返还给驱动。本轮改善针对测得的 PyTorch allocated 峰值；不能据此承诺 `nvidia-smi` 占用会按相同幅度变化。


## 最终保留结果

本轮保留速度与峰值显存。32K输入、Batch8的整轮峰值由73.5107降至53.4131 GiB（−27.34%）。全部16点及48正式轮保存在项目根目录 `A800最终测试/BetterMemory_速度与峰值显存/`。峰值为PyTorch allocated，含权重与临时张量；仍高于单纯KV存储。没有重新评估完整质量集。
